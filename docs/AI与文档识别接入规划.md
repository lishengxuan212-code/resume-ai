# AI 与文档识别接入规划

版本：V0.1，方案建议，尚未实现。

前置依据：首次开发边界.md、homepage-design.md。

当前进度：用户已认可首页初稿；源码包括入口交互，尚未连接真实文件上传、文档识别、AI 或账号服务。当前环境自动浏览器验证仍受阻，不将用户认可等同于自动化 QA 通过。

## 一、下一阶段交付目标

让用户上传 PDF/DOCX 或填写经历后，获得可核对的结构化资料；结合目标岗位和方法论，经最多 3 个关键事实追问，生成事实有依据的简历内容，再通过固定模板导出 PDF。

材料提交后约 5 分钟完成首轮优化是待实测的产品目标。识别耗时、AI 耗时和等待用户回答时间分别记录，不能直接承诺所有文档都能达成。

首版继续使用现有 AI 模型，不训练模型，不将原始简历自动用于训练。先搭建可版本管理的方法论规则。

## 二、推荐结构

保留现有 React/Vite 前端，增加一个 Node.js 后端，统一负责文档解析、模型调用、任务状态和 PDF 导出。浏览器只访问自己的后端，不保存 AI 密钥，也不直接调用模型厂商接口。

推荐以能提供持久卷的单实例 Node 容器作为初期后端；静态前端可以独立托管，或由后端同域提供。先用 SQLite 持久化任务元数据和结构化内容，以私有临时目录保存原文件。具体托管商及费用需选定后核实，不默认普通静态托管支持这些能力。

现有项目保留模板 Worker 构建，但不能把 Node 文档处理和浏览器 PDF 导出代码直接塞进 Worker 并假定兼容。实际后端部署方案要单独验证。

初期单实例、有限并发，先不增加 Redis、微服务或向量数据库。如果后续扩展到多个实例，再迁移到共享数据库、队列与私有对象存储。文件生命周期、访问校验和模型适配从首版就保留清晰接口。

## 三、文档上传与识别

### 上传

- 沿用前端 PDF/DOCX、10 MB 限制，后端重复验证文件大小、文件签名和实际结构；不只相信扩展名或浏览器 MIME。
- 单次处理一个文件，暂定最多 10 页；超限明确提示，不静默截断。
- DOCX 检查 ZIP 解压后体积和条目上限；解析任务设置内存、时限和并发限制。
- 随机生成 documentId，原文件存到私有目录；禁止用户文件名作为服务器路径。
- 游客采用不可猜测的会话凭据验证所属关系。知道 documentId 不能直接下载他人的文件。
- 展示实际状态：接收中、识别中、需要核对、识别失败；不能用计时动画伪装完成。

### 分类处理

| 文件情况 | 处理方式 | 需要保留的信息 |
|---|---|---|
| 文字型 PDF | 使用 PDF.js 提取每页文字和位置，整理行与段落；多栏顺序单独检测 | 页码、文字片段、坐标、解析告警 |
| DOCX | 使用 Mammoth 提取段落文字；根据实际样本补充表格与文本框的归组 | 段落/单元格定位、原文、转换告警 |
| 扫描或混合 PDF | 先检测各页文字质量，仅将缺字、图片页送 OCR；按页合并 | OCR 来源、页码、可用的置信信息 |
| 加密、损坏、解析失败 | 明确说明原因，允许换文件或在线填写 | 错误码、可恢复动作 |

PDF.js 官方示例提供 Node 端文本提取；Mammoth 支持 extractRawText，但并不保留完整排版。因此“提取成功”不等于“简历结构正确”。表格、多栏、艺术字体、扫描件必须作为专门的验证样本。[1][2]

先交付文字 PDF/DOCX，再接入 OCR 回退。OCR 上线前遇到扫描页必须明确提示暂不支持，不能把空文本当成完整识别结果。对外完整开放前，验证扫描与混合页回退，并核算 OCR 成本。

识别质量根据文本覆盖、乱码、字段缺失和版面冲突判断，不能伪造一个没有校准依据的“准确率”。识别不确定时，把相关原文与待核对字段一起展示。

不把 DOCX 转换出的 HTML 直接嵌入页面；优先使用纯文本，所有显示内容转义。上传文件和招聘要求都作为不可信资料处理，其中的“忽略规则”等文字不能成为系统指令。

## 四、统一简历数据

把上传和在线填写转换到同一数据结构，字段包括：基本资料、教育背景、经历、技能、求职方向、原始片段、解析告警、用户确认状态。

每条事实保存来源：PDF 页码/文字片段、DOCX 段落或用户回答编号。推荐岗位、模型推断与用户明确提供的事实分开存放。没有的信息记为空，不猜姓名、日期、职责或指标。

建议核心对象：

- Document：文件类型、私有存储引用、解析状态、过期时间。
- SourceBlock：原文片段、页码/段落、来源类型、解析告警。
- ResumeFacts：结构化事实及 sourceIds、用户确认记录。
- TargetRole：用户目标或已确认的推荐方向、招聘要求。
- Question：问题、追问原因、关联事实、用户答案；首轮总计最多 3 个。
- ResumeVersion：基于哪个事实版本、方法论版本、模型配置生成，以及逐条内容的 sourceIds。
- Job：任务状态、阶段、尝试次数、错误和用量；不记录完整简历到普通日志。

用户纠正原文或回答问题时增加事实版本号；生成结果必须绑定该版本，防止展示过期结果。

## 五、方法论怎样接入

用户整理的文字笔记尚未提供。先定义导入格式和规则执行方式，待提供后提炼，不虚构已经拥有的方法论。

规则按三层组织：

1. 通用规则：真实、清晰、突出个人贡献、避免空泛、不过度堆砌术语。
2. 岗位规则：运营、产品、技术、市场、电子信息、AI、财务、建筑的关注点；复合岗位可组合适用规则。
3. 追问规则：在哪类缺口下问什么事实、何时跳过、没有数据时怎样表达。

每条规则应包含 ruleId、版本、来源笔记、适用岗位、触发条件、修改要求、禁止项、冲突优先级和示例。通用硬约束优先于岗位偏好。

示例格式（只是规则草案，不代表已从用户笔记提炼）：

```json
{
  "ruleId": "truth-001",
  "version": "0.1",
  "status": "draft",
  "source": "本轮产品边界",
  "roles": ["all"],
  "when": "经历没有可核实的结果数据",
  "action": "基于已有事实描述具体行动与可确认的交付物",
  "forbidden": ["编造百分比", "把团队成果全部归给个人"],
  "priority": "hard"
}
```

首版把规则放在代码仓库的版本化文件中，根据岗位和缺口选择相关规则提供给模型。规则数量少时无需先搭建向量数据库。原始视频笔记与整理后的可执行规则分开管理。

## 六、AI 内容生成流程

1. **结构化与诊断**：将提取文本转成 ResumeFacts，标出不确定项；用户已经填写的确定字段无需再次识别。
2. **确定目标**：有岗位时分析要求；没有岗位时结合经历和少量偏好推荐 2—3 个方向，展示依据，由用户选择。推荐不等于承诺适合所有相关岗位。
3. **必要追问**：合并关键缺口，最多 3 个事实问题，允许跳过。目标选择属于基础设置，事实追问仍受总数限制。
4. **生成内容**：输入已确认事实、目标岗位和适用规则，输出结构化简历内容，不直接输出任意 HTML。
5. **校验**：验证数据结构、字段长度、来源引用、日期及新增数字/实体；对职责提升、成果归属等语义问题增加校验。模型自查只作辅助，不保证真实性，仍需用户核对关键事实。
6. **排版导出**：固定模板渲染已通过校验的内容，检查中文字体、分页、文字溢出，再生成 PDF。

输出 JSON 只是格式约束，不能保证语义与事实正确。以 DeepSeek 为例，官方 JSON Output 文档还提示空内容等异常情况，因此后端仍需校验、处理截断和有限重试。[3]

先实现可替换的模型适配器，通过配置选择供应商、模型和超时。候选模型要用同一批中文简历比较事实忠实度、表达质量、延迟和单份成本后选定；本方案不先锁定某个模型，也不依据网站 UI 偏好推断模型偏好。

在服务端保存密钥；实施时通过部署环境安全配置，不要求在聊天或 GitHub 中粘贴完整密钥。

## 七、接口与任务状态

以下为建议接口，实际字段在实现前固定版本：

| 接口 | 职责 |
|---|---|
| POST /api/documents | 接收文件，创建解析任务，返回 documentId/jobId |
| GET /api/jobs/:id | 验证会话后返回状态和可读进度 |
| GET /api/documents/:id/extraction | 返回提取片段、字段和告警 |
| POST /api/resumes | 从提取结果或在线填写创建事实版本 |
| PATCH /api/resumes/:id/facts | 更新用户核对后的事实并递增版本 |
| POST /api/resumes/:id/diagnose | 岗位分析、推荐与必要追问 |
| POST /api/resumes/:id/generate | 提交已确认目标与回答，创建生成任务 |
| GET /api/resumes/:id/versions/:version | 返回已校验内容和来源关联 |
| POST /api/resumes/:id/versions/:version/export | 固定版本 PDF 导出 |
| DELETE /api/resumes/:id | 删除所属材料、内容与导出文件 |

任务状态为 queued → processing → awaiting_confirmation/awaiting_answers → completed，失败进入 failed。等待用户操作不占用解析/模型并发槽。

生成请求使用幂等键防止双击重复扣费。超时/限流有限重试，格式错误可最多修复一次；失败保留用户已填信息并允许重试。进程重启后恢复或标记中断任务，不让状态一直显示处理中。

## 八、数据与费用边界

- 游客原文件和生成材料建议最长保留 24 小时；到期清理或用户主动删除。期限须在产品中提前说明，清理机制需实际实现。
- 原文件、解析正文、联系方式、导出简历不进入 GitHub，普通日志不输出完整个人内容。
- 只向 AI/OCR 服务发送必要内容，并说明用途；联系方式可在生成时剥离，排版时再由可信事实回填。
- “用于处理这次简历”和“用于后续改进/训练”分开；默认不用于训练，后者需另行明确授权。
- 保留月预算 1,000 元的规划：AI 600、托管/数据库/存储 200、OCR/波动与失败重试预留 200。它是预算分配，非供应商报价；选定服务后再核实可行性。
- 记录每次 token、OCR 页数、耗时、重试和估算费用；逐份汇总。用真实样本得到单份成本后才能估算容量。
- 按任务并发和服务端游客额度限流，设置费用预警及达到上限后的停止策略。即使未注册也不能无限生成；首次完整体验额度提前说明。

## 九、实施顺序与验收

| 阶段 | 交付 | 验收 |
|---|---|---|
| A：真实材料输入 | Node 后端、会话、PDF/DOCX 上传、文字提取、核对页面 | 文字 PDF、双栏、表格 DOCX、空白、损坏、加密与超限文件均有明确结果；不静默漏页 |
| B：方法论与 AI | 规则文件、模型适配、结构化诊断、岗位确认、最多 3 问、生成 JSON | 字段可校验，事实可追溯；跳过问题仍可完成；不编造数值与责任 |
| C：交付闭环 | 扫描页 OCR、模板渲染、PDF 下载、错误恢复、成本记录 | 混合 PDF 可识别或明确失败；中文 PDF 无截断；重复操作不重复收费 |
| D：小范围试用 | 日志脱敏、限额、清理、跨文档样本回归 | 测得完成率、延迟、用户反馈及成本，再决定扩大推广 |

建议第一批准备 24 份虚构或明确授权的样本，覆盖八个方向，每方向包含经历少、经历完整和复杂格式。另加提示注入、事实冲突等异常样本；未经授权不把真实简历放进测试仓库。

阶段 A 可先于最终方法论完成；阶段 B 要接入经过确认的规则和模型配置。界面允许演示与真实处理区分，不能在尚未接入服务时显示“已优化完成”。
